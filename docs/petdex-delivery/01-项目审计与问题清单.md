# 项目审计与问题清单

## 1. 审计对象

本次审计覆盖：

- 原需求文档：`docs/petdex-product-requirements.md`
- 原业务报告：`docs/petdex-product-business-report.md`
- 首轮采集目录：`docs/petdex-analysis/`
- 二轮采集目录：`docs/petdex-analysis-round2/`

目标是找出前序材料中不适合直接进入开发的内容，并形成修正版交付资料。

## 2. 总体判断

前序材料在信息量上是充分的：已经覆盖页面结构、功能模块、支付逻辑、工作台状态机、艺术相册、作品库、下载页、云养广场和 FAQ。

但从项目经理角度看，前序材料存在“证据质量混杂”和“产品结论边界不清”两个核心问题。必须在进入开发前完成治理，否则研发和设计会误把不可靠截图、推断逻辑或竞品文案当成正式需求。

## 4. 文档级问题

### 4.1 原需求文档问题

优点：

- 功能覆盖面广。
- 页面结构完整。
- 支付流程第二轮补充后较准确。
- 有 API、数据模型和状态机。

问题：

- 太像竞品拆解，缺少自有产品口径。
- 缺少版本范围，容易导致 MVP 过大。
- 对支付、客户端、AI 生成服务的研发风险说明不足。
- 部分截图来自竞品真实 UI，不应作为最终设计稿。

修正：

- 新增 `02-修正版产品需求PRD.md`，按自有品牌产品重写。
- 将“必须做”和“可后续做”分开。
- 将支付、客户端、AI、作品库、社区拆成独立模块。

### 4.2 原业务报告问题

优点：

- 市场和商业模式分析清楚。
- 能解释为什么这个产品不只是 AI 图站。

问题：

- 对获客渠道、市场定位和差异化仍偏泛。
- 缺少具体增长实验和指标优先级。
- 缺少商业化上线前的验证方法。

修正：

- 新增 `03-业务与市场分析修正版.md`。
- 强化目标用户、价值主张、增长实验和指标树。

### 4.3 原采集文件问题

问题：

- 原始目录里既有有效截图，也有错误截图。
- `interaction-clicks.json` 为空数组，不能作为交互证据。
- `payment-01-tier-select-revealed.png`、`payment-02-before-order.png`、`payment-03-qr-pending-simulated.png` 是早期误切截图，不应使用。
- `payment-correct-01-tier-select.png` 实际仍未呈现套餐选择状态，不作为有效主证据。
- `payment-correct-02-pay-default.png`、`payment-correct-03-pay-qr-state.png` 是有效支付 UI 参考，但后者为前端复现。

修正：

- 新增 `05-证据目录与采集文件说明.md`。
- 标注每份材料可信度。

## 5. 最终取舍原则

后续项目执行只遵循以下原则：

1. 不复制竞品品牌、素材、完整文案、客户端文件名和案例图。
2. 用竞品作为结构参考，不作为视觉设计稿。
3. MVP 先做桌宠生成主链路，不做完整社区。
4. 支付先 mock 或人工确认，真实支付放到商业闭环验证之后。
5. 客户端是核心交付，不是附属页面。
6. 艺术相册和云养广场是增长模块，不进入第一阶段。
